What this mockup is proposing

Everything here is clickable. Switch layouts, drag sessions between panes, and pop one out into a real window you can drag to another monitor.

Why it is cheap to build

The hard part is already done. Each session is its own tmux session with its own output stream, and the app already keeps one live terminal per session in memory - it just hides all but one. A grid is mostly a matter of showing more than one at a time and letting each keep its own stream.

  • Panes - the pane objects already exist; today the app hides the inactive ones. In a grid they stay visible, and each reports its own size so tmux reflows to the pane rather than to the window.
  • Streams - one open stream per visible pane instead of one per window. Four panes is four streams, which is fine; the browser's ~6 per origin limit is the ceiling, so a grid caps sensibly at four.
  • Pop-out - a second native window in the app, pointed at the same local server with the session id in the URL. Same page, one pane, no sidebar. Close it and the session goes back into the grid.

What needs deciding

  • Focus - one pane owns the keyboard. Clicking a pane focuses it, and that is the one the sidebar marks.
  • Layouts per screen - remember the layout, and which session sat where, so reopening the app restores the wall you left.
  • Attention - with four panes visible, a session needing you should pulse its own pane border, not just the sidebar dot.
  • Pop-out lifetime - a popped-out session keeps running if that window closes; it simply returns to the grid.

Rough size

Grid + drag-to-pane + focus: a day. Pop-out windows: another day, mostly native window plumbing on the Swift side. Layout persistence: a couple of hours. Nothing here needs a change to the server or to tmux.
