Mattdaemon - stability audit

Everything reported as "the app gets buggy after a while": the corrupted screen, sessions that will not close, the red dot that wants nothing, and the dead Attach button. Seven defects found and fixed, each with the mechanism named and a test that fails without the fix. Plus what the measurements did not support, and where the remaining time is best spent.

Fixed

01

Attach did nothing in the app

fixed
Symptom
"The attach button is not working at the moment." Intermittent-looking, because paste and drag-and-drop kept working.
Mechanism
The page opens a file picker with <input type="file">. A WKWebView never opens one on its own - the host app must implement runOpenPanelWith. It was not implemented, so the click was swallowed in silence. In a browser the same page works, which is what made it look like a bug that came and went.
Fix
Implemented the delegate with an NSOpenPanel. The completion handler is called on cancel too - WebKit keeps the input disabled until it is, so a dropped cancel would kill Attach for the rest of the session.
Certainty
Certain. A missing delegate method cannot half-work.
02

The corrupted, overlapping screen

fixed
Symptom
Text drawn over itself at two different widths, and escape-sequence debris printed as literal text - 5;180m in your screenshot.
Mechanism
Each session keeps a 32 KB scrollback buffer that is replayed verbatim to a terminal when it reconnects. When the buffer passed 32 KB it was trimmed with a blind byte cut - del buf[:excess] - which can slice an escape sequence in half. The buffer then begins with the tail of a sequence. A fresh xterm prints that tail as text and its parser is left in the wrong state, so everything after it renders shifted. It needed both a long-running session (to wrap the buffer) and a reconnect (sleep, wake, network blip) - which is exactly why it felt random.
Evidence
Reproduced directly against the real buffer code: 
old cut begins with: b'0m'   <- printed as text, parser desynced
new cut begins with: b'\x1b[1mDone\x1b[0m...'
Fix
Trim to the next escape sequence rather than to an arbitrary byte, so a replay always starts somewhere a terminal can begin reading. Multi-byte characters are no longer split either.
Certainty
Mechanism proven. The debris in the reproduction is the same shape as the debris on your screen.
03

Red dot on a session that wants nothing

fixed
Symptom
"A session is done, but it's showing red like it needs me, and then I'm clicking on it and I don't need anything."
Mechanism
The classifier searched the whole visible pane for prompt text: do you want to, y/n, ❯ 1. yes. Real panes here are 53 lines. An already-answered permission box still sitting in the transcript kept the session red, and so did any output that merely contains "(y/n)" - documentation, a code block, a script's own help text.
Aggravator
The Claude Code hooks that stamp a precise state (@webstate) are not installed on this Mac - checked: ~/.claude/settings.json has no webterm-state hook. So for local sessions the pane text is the only signal there is, and it was being read at its noisiest.
Fix
Only the live region counts - the last 20 lines, where a terminal puts what it is asking now. A real waiting box still reads red; an answered one, and mere prose, do not.
Certainty
Mechanism proven with 53-line panes matching the real ones. Installing the state hook on the Mac would make this exact rather than heuristic - see opportunities.
04

Every local action waited on the VPS

fixed
Symptom
The app "gets one more buggy" the longer it runs, with no single trigger.
Mechanism
Both status endpoints called the box inside the request, with a 6-second timeout. Every status poll therefore cost a network round trip, and a slow or unreachable box made every poll take up to six seconds - while the page kept firing a new one every three (see 05). Your Mac's status was hostage to a machine that also runs the Claude farm.
Measured
The box answers in 0.13-0.17s right now, so this is not what you are seeing this minute. It is what you see whenever that box is loaded - and it has a history of exactly that.
Fix
A background thread asks the box on its own clock and leaves the answer in a snapshot. Requests read the snapshot and return at local speed, always. The VPS section goes "offline" if the snapshot ages past 25s instead of freezing the app.
05

Status polls piled up on themselves

fixed
Mechanism
The page polled on a fixed setInterval with no guard: if a poll took longer than its interval, the next one fired anyway. The browser queues those against its ~6-per-origin limit, so the backlog delays whatever you do next, and the server is asked to redo expensive work it has not finished. It also kept polling at full rate while the window was hidden.
Measured
Against a status endpoint made to take 2s, watched for 24s:
 BeforeAfter
Status polls issued83
Size heartbeats177
Polls while hidden (12s)40
Fix
Each poll schedules its own next run, never overlaps itself, backs off when answers are slow, and goes quiet when the window is hidden. The size heartbeat speaks when the size changes and otherwise just often enough to stay inside the server's 6s TTL.
06

Closing a session could stall everything else

fixed
Symptom
"Sometimes it's difficult for me to close a session."
Mechanism
When a session disappears, its view is torn down - which terminates a tmux client and waits up to 5 seconds for it. That teardown ran while holding views_lock, the lock every keystroke, resize and stream attach needs. So the moment a session ended, the whole app could freeze for seconds. Two of them, ten seconds.
Fix
Views are removed from the map under the lock and torn down outside it, and the wait is 1s before a kill. Nothing user-facing waits on a dying tmux client any more.
Certainty
Mechanism certain from the code; how often it fired in your hour is not measurable after the fact.
07

The sidebar marked a session you were not in

fixed
Mechanism
Two causes. A blip on the box dropped its sessions from one poll, which the app read as "gone" and answered by moving you into an unrelated local session and marking that. And on reload it selected whatever tmux listed first, rather than where you were.
Evidence
Reproduced: forcing a blip put the app in CRM - the session marked in your screenshot.
Fix
A session counts as gone only when the machine that owns it says so; the app remembers where you were across reloads. While a host is unreachable, nothing is marked rather than something wrong.

What the numbers did not support

The browser was not running out of connections. The obvious theory for "buttons stop working" is the ~6-connections-per-origin limit being eaten by streams and polls. Measured against the real page, the browser queues excess polls rather than opening more sockets: peak concurrent connections stayed at 3, and a close-session request still answered in 0.04s even with the status endpoint crawling. The pile-up is real and worth fixing (05), but the damage it does is backlog and wasted server work, not a starved connection pool.

The status poll is not expensive at your scale. With 6 sessions it took 61ms before the caching change and 35ms after. Worth having - it grows with session count, and the box runs the same code for its 8 - but it is not what made your app sticky.

Still open

08

The "after an hour" feeling has no single proven cause

open
Status
Four of the seven fixes above each degrade over time or with session count, so the symptom should be materially better. But nothing yet proves a leak over hours, because that needs the app watched over hours.
Now measurable
Settings has a How it is running panel: how long polls actually take (typical and slow), how many terminals are attached, how many are stale, stream and thread counts, and how fresh the VPS snapshot is. When it next feels sticky, open it before restarting - if stale is above zero, or the poll timings have crept into seconds, that is the leak, named.
Also served
curl -s localhost:8722/api/terminal/health
09

The status hook is missing on this Mac

open
Detail
On the box, Claude Code hooks stamp each session's exact state. On this Mac they are not installed, so local dots are inferred from pane text and the process tree. Finding 03 makes that inference much less noisy, but it stays an inference.
Fix available
Install the webterm-state hook locally and the dots become exact: attention comes from Claude's own PermissionRequest, idle from its Stop. Roughly an hour, and it removes a whole class of wrong-colour complaints. Not done here because it edits your global Claude config, which is yours to decide.
